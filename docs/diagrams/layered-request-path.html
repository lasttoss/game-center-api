Architecture · game-center-api

One request, and the two datastores that do different jobs

A layered Spring service where each layer has one job: the controller speaks HTTP and nothing else, the service decides, the repository talks to Mongo — and the document shape never reaches the client because a mapper stands between them.

Spring Boot · MongoDB for the catalogue, leaderboards and player data · Redis for caches and pub/sub · stateless JWT · one error envelope for every endpoint
Why the controller stays thin

A controller that decides is a rule that cannot be tested without HTTP and cannot be reused by a scheduled job. Keeping it to transport is what makes the service layer testable on its own.

Why stateless auth matters here

No session to lose means an instance can be replaced or scaled out at any moment, which is the property the container setup depends on. A token that has to be renewed is a client concern.

Errors as data, not as prose

One envelope and one enum mean a client parses one shape, and an operator can group failures by code. A service whose every endpoint invents its own error body is a service whose errors are read one at a time.
